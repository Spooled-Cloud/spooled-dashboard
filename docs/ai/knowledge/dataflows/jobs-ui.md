# Jobs UI

Pages under `/jobs`, `/jobs/[id]`, `/jobs/dlq`. Clients in `src/lib/api/jobs.ts`. Create/bulk/DLQ components under `src/components/jobs/`.

`GET /api/v1/jobs/status?ids=` returns `{ id, status, queue_name, retry_count, created_at, completed_at }`, not `attempt`/`max_retries`. `jobsAPI.batchStatus` maps `retry_count` onto `attempt`. The lookup UI cannot show max retries; that field is not on the batch payload.

`GET /api/v1/jobs/stats` is `{ pending, scheduled, processing, completed, failed, deadletter, cancelled, total }`. It has no `by_queue`/`by_type`/`by_hour`.

`GET /api/v1/jobs` summaries include `job_type` from `payload.job_type` (empty string when absent). `jobsAPI.list` maps that onto `Job.job_type`. Filtering is server-side (backend 0.1.122): `status` is one value or ONE comma-joined list (several statuses are never fanned out into several requests), `q` is a case-insensitive match on a job id **prefix** or a substring of the queue name or `payload.job_type`, `job_type` is an exact match, `tag` is a `jsonb ?` match, and `created_after` (inclusive) / `created_before` (exclusive) are RFC 3339 instants. `jobsAPI.list` sends exactly one request per call: the old 500-row client scan (`SEARCH_MAX_SCAN`), its id/job_type substring filter and the `GET /jobs/{id}` fallback are gone, because a full job id is a prefix of itself. `JobsListPage` sends the text filters (search, queue, type, tag) once typing pauses (300 ms) and the dates at once; `parseJobFilters` / `jobFiltersToQueryString` (`src/components/jobs/job-list-filters.ts`) keep all of them in the URL. The two date pickers are inclusive local days: `createdRange` sends the start of `from` and the start of the day after `to`, as UTC `Z` instants (a `+` offset would have to survive a query string). An unknown status, an unparsable date or `after >= before` is a 400 whose message the list shows. The status select has no **Failed** option: no job ever gets that status, a job that runs out of retries is `deadletter`; a legacy `?status=failed` link opens the dead-letter jobs, and the dashboard's own links and Recent failures panel use `deadletter`.

`GET /api/v1/jobs` has no total: it returns a bare array, so `jobsAPI.list` only counts what the page proves. Whether another page follows comes from the `X-Has-More` response header, read through `apiClient.getWithHeaders`. A browser reads a cross-origin header only when the API's CORS layer exposes it (`Access-Control-Expose-Headers: x-has-more`, backend CORS request pending), so the list adapts: until a response shows the header it asks for `per_page + 1` rows and counts the extra row (`rows.length > per_page`); once a response carries the header it asks for exactly a page and trusts the header, and a response without it puts the list back to probing (`hasMoreHeaderReadable`, `resetHasMoreProbe` for tests). At `per_page` 100 (the backend cap) no probe row can arrive, so a full page counts as 'maybe more'. The exact count is a separate query, `jobsAPI.getListTotal`, which calls `GET /jobs/stats` for an unfiltered view or one status, optionally within one queue, and returns `undefined` for multi-status. `JobsListPage` applies it with `withExactTotal` only when `hasUncountableFilters` is false (no search, type, tag or date filter, which stats cannot count). `jobsAPI.list` returns a `JobListPage`: `total` / `total_pages` are floors derived from the rows read, and only `withExactTotal` sets `totalExact: true`. While `totalExact` is false (a search, type, tag or date view, or stats unavailable) the pagination prints `Showing 26–50` and `Page 2`, never a guessed "of N results" / "of M pages", and Next follows `hasMore` (`DataTablePagination` props `totalExact`, `hasMore`, `itemCount`; `hasMore` is false at `JOBS_LIST_MAX_PAGE`). Backend 0.1.121 ignores `q`, `job_type` and the created window and answers with the unfiltered list and no `X-Has-More`; when any of those was sent and the header is absent, `list` returns `filtersUnsupported: true` with no rows and the page shows "This server version cannot filter by search, type or date yet" (`JOBS_FILTER_UNSUPPORTED_MESSAGE`) instead of passing the unfiltered rows off as results. Queue, status and tag work on both versions. Until the API's CORS layer exposes `X-Has-More`, a browser cannot tell that case from a 0.1.122 backend, so a search, type or date view shows the same notice. The count has its own key outside `jobs` (`src/lib/query-client.ts`, `jobTotals`), so realtime invalidations do not refetch it, and it has a 60 s stale time. Page jumps stop at `JOBS_LIST_MAX_PAGE` = 200. `q` with no time window is a sequential scan on the server (about 65 ms at 120k rows); pairing it with a date range keeps it index-backed.

There is no `failed_at` column. The details mapper sets `Job.failed_at` from `completed_at`/`updated_at` when status is `failed` or `deadletter`. A pending retry has `last_error` + `scheduled_at`; that maps onto `next_retry_at` so the timeline shows Next Retry instead of Scheduled.

The job timeline (`JobTimeline` in `JobDetailsPage.tsx`, rows from `buildJobTimeline` in `src/components/jobs/job-timeline.ts`) reads `GET /api/v1/jobs/{id}/history` (backend 0.1.122; `jobsAPI.getHistory`, first 100 events, oldest first, `X-Has-More` when readable). Each recorded event shows its label (`processing` = Started, `completed`, `retry_scheduled`, `deadlettered`, unknown types humanized), time, the worker (linked to `/workers/{id}`) and a one-line summary of its `details` (retry number, next run, error, batch claim; `organization_id`, `worker_id` and `lease_id` are hidden). History rows exist only where backend code writes them (REST claim, complete, fail, the scheduler's dead-letter sweeps, `QueueManager::enqueue`; REST create and gRPC paths write none), so the job's own fields add what no row can say: Created, Cancelled, the outcome of a job finished over gRPC, and the upcoming Next Retry. A 404 (backend before 0.1.122), an empty history or any other failure falls back, without a toast, to the timeline derived from the job fields alone (a 500 adds a one-line note). The history query key carries the job's status and attempt, so a state change reads it afresh, and it sits under `jobs` so realtime events refresh it.

`GET /api/v1/jobs/dlq` is the same `JobSummary[]` (`attempt`, top-level `job_type`, `last_error`), not a full `Job`. `jobsAPI.listDeadLetter` uses the list summary mapper and maps `last_error` onto `Job.error`.

DLQ page (`src/components/jobs/DeadLetterQueuePage.tsx`) shows up to 100 rows (`:58`). The dead-letter count is `GET /jobs/stats` for the queue filter (`:63-69`) and is never below the rows on screen (`:69`). Purge sends `limit` equal to the count in its dialog, capped at `DLQ_PURGE_MAX_LIMIT` = 10000 (`src/lib/api/jobs.ts:264-265`; `DeadLetterQueuePage.tsx:244`). It refuses a count below 1 (`:95-98`) and warns when more jobs exist than the cap (`:383-384`). Retry Selected sends `job_ids`; `DLQ_RETRY_MAX_LIMIT` = 100 (`jobs.ts:266-267`) is the backend retry cap. Changing the queue filter clears the selection (`:186-190`).

Create Job (`src/components/jobs/CreateJobDialog.tsx`) sends `scheduled_at` as an RFC 3339 UTC instant. `localDateTimeToIso` (`src/components/jobs/job-form-utils.ts:29-33`) reads the `datetime-local` value as the browser's local time (`CreateJobDialog.tsx:128-141`), and an unparseable date stops the submit (`:129-132`). The form says the time is local (`:274`). Max retries go through `parseMaxRetries` (`job-form-utils.ts:20-22`): an explicit 0 stays 0, values clamp to 0..100, and only an empty or non-numeric field falls back to 3. `BulkEnqueueDialog.tsx:125` uses the same parser. The Backoff Type select is gone, because the backend has no per-job backoff. The queue field is a text input with a datalist of existing queues (`CreateJobDialog.tsx:184-196`), so a new queue name can be typed.

Job details (`src/components/jobs/JobDetailsPage.tsx`) has no Delete. The backend has no hard-delete route: `DELETE /jobs/{id}` only cancels, and returns 409 unless the job is pending or scheduled. Cancel is shown only for those two states (`JobDetailsPage.tsx:406`; buttons at `:471-479` and `:692-700`). `jobsAPI.cancel` (`jobs.ts:497-499`) is the only client for that route, and `jobsAPI.delete` was removed.

## Workflows

`POST /api/v1/workflows` returns `{ workflow_id, job_ids, status }`, not a full `Workflow`. The backend has no `job_type` column; the client writes it into each job `payload` when that payload is a JSON object (same as job/schedule create) and sends timeouts as `timeout_seconds`. Arrays, strings, and other JSON values are sent as-is — spreading them would turn `"hello"` into `{0:"h",...}`. `GET /workflows/{id}` still sends `job_type: "job"`; `workflowsAPI.get` maps `payload.job_type` onto the UI field.

Usage meter: the workflows row in `UsageWidget` is labelled **Active workflows** (`src/components/usage/UsageWidget.tsx:206`); the admin org usage list says **Active Workflows** (`src/components/admin/AdminOrganizationDetail.tsx:871`). The backend counts only pending/running workflows against `max_workflows` (`spooled-backend/src/api/handlers/workflows.rs:668`), so the meter is not a total of all workflows.

Cancel is offered only while a workflow is `pending` or `running`. `canCancelWorkflow` (`src/lib/api/workflows.ts:168-170`) gates the list and details buttons (`src/components/workflows/WorkflowsListPage.tsx:240`, `WorkflowDetailsPage.tsx:303`). A failed cancel shows the backend message in the toast (`WorkflowDetailsPage.tsx:217-221`).

## Organization settings

`PUT /api/v1/organizations/{id}` accepts `name`, `billing_email`, `settings`. There is no `description` column; the settings page stores it in `settings.description`. The backend preserves `webhook_token` when settings are replaced. `settings` is `serde_json::Value`; description writes merge only a plain object (spreading an array/string would become `{0: ...}`).

Billing email confirmation (backend 0.1.117): email sign-in only resolves an org by a **confirmed** billing email (`billing_email_verified_at`). An address set through the API or at onboarding (`POST /organizations`) starts unconfirmed. `BillingEmailVerification` (`components/settings/OrganizationSettings.tsx`, Access card) calls `POST /organizations/billing-email/verification` to send a code and `POST /organizations/billing-email/verify` to confirm it, then invalidates the org detail query.

A changed billing email waits in `pending_billing_email` (`src/lib/types/index.ts:310`). Organization Settings shows it as **Pending confirmation** under Billing Email (`src/components/settings/OrganizationSettings.tsx:511-513`). The verified address keeps its Confirmed badge and stays the sign-in email (`OrganizationSettings.tsx:102-105`), and the code-sent fallback is the pending address (`:62`).

## API keys and admin custom limits

Settings page `/settings/api-keys` → `ApiKeysListPage.tsx` (+ `CreateApiKeyDialog.tsx`); client `src/lib/api/api-keys.ts`.

API key `rate_limit` is requests per minute (1-10000). The create dialog says it can only lower the plan's limit, never raise it (`CreateApiKeyDialog.tsx:305-306`; type comments `src/lib/api/api-keys.ts:12`, `:45`, `:62`). The list shows it as `requests/min` (`ApiKeysListPage.tsx:225`). The scope helper documents `*` and prefix patterns such as `orders.*` (`CreateApiKeyDialog.tsx:283-289`). Expiration is read as the browser's local time and sent as a UTC ISO instant; a past or invalid date is rejected before the request (`CreateApiKeyDialog.tsx:102-120`).

Keys with `is_system: true` are the ones the email-login flow creates for dashboard sessions (`src/lib/api/api-keys.ts`). They show a **System** badge, and revoking one warns that dashboard sessions end. The key behind the current session cannot be revoked: its Revoke button is disabled, `handleRevoke` refuses it, and its row shows **Current session**. The guard does not fail open: when `/auth/me` never loaded (`user.api_key_id` unknown), `resolveCurrentKeyId` (`src/components/settings/current-session-key.ts`) fetches `/auth/me` again before Revoke goes on, and Revoke is refused with a toast if the id is still unknown.

Every row has an **Edit** button (`EditApiKeyDialog.tsx`, `PUT /api-keys/{id}`): rename (1-100 characters) and a **Key is active** switch. Only changed fields are sent, so queues, rate limit and secret stay as they are. Switching a revoked key back on is charged against the plan's API-key cap (system keys excepted) and can be refused with 429 `QUOTA_EXCEEDED` (`details.current` / `details.limit`); the dialog stays open and says so (`apiKeyCapMessage`). The session key's switch is disabled, as Revoke is, and `handleSubmit` refuses `is_active: false` for it (`isCurrentSession`, or the id from the store / a fresh `/auth/me`); when the session key is unknown it fetches `/auth/me` again before switching any key off and refuses, with a message, if it is still unknown. Renames and re-activations never need the session key. An expired key stays expired when switched on (`expires_at` is not editable).

Admin Custom Limits (`AdminOrganizationDetail.tsx`) edits every field in `CUSTOM_LIMIT_FIELDS` (`:77-91`), including Rate Limit Burst, Job Retention (days) and History Retention (days). The inputs are rendered from that list (`:725`). Save goes through `mergeCustomLimits(existing, initial, edited)` (`src/lib/utils/custom-limits.ts:38-65`, called at `AdminOrganizationDetail.tsx:277`). It starts from the org's current `custom_limits` and changes only the fields the operator edited, because the backend replaces the stored object on save (`spooled-backend/src/api/handlers/admin.rs:452-459`). The eight resource caps (`UNLIMITED_CAPABLE_KEYS`, `custom-limits.ts:15-24`) take an Unlimited checkbox and save as `-1`. A stored `null` or `-1` reads back as Unlimited (`limitToFormValue`, `custom-limits.ts:27-30`). Settings fields (payload size, rate limit, retention) cannot be unlimited. A per-key `null` survives a save (`custom-limits.ts:6`).

## Workers

`GET /api/v1/workers/{id}` returns `WorkerResponse` (`max_concurrency`, `current_jobs`, `registered_at`), not the DB `Worker` row (`max_concurrent_jobs`, `current_job_count`, `created_at`). List uses `WorkerSummary` (`max_concurrency` / `current_jobs`). Backend status is `healthy`/`degraded`/`offline`/`draining`; the UI maps `healthy` with `current_jobs === 0` to `idle` and other healthy/degraded workers to `active`.

`GET /api/v1/dashboard` worker totals are `{ total, healthy, unhealthy }` (`unhealthy = total - healthy`). That is not an idle count. `normalizeDashboardData` maps healthy → `worker_status.active` and unhealthy → `offline`; idle stays 0 because the overview payload has no per-worker `current_jobs`. The workers list page is the source for idle.

The list summary (`WorkerSummary`) has no `registered_at`, so `transformWorkerSummary` (`src/lib/api/workers.ts`) leaves `started_at` undefined and the list shows no start time. The detail page's Started At comes from `registered_at`, and utilization is 0 when concurrency is 0. Backend 0.1.122 adds `jobs_processed` and `jobs_failed` (int64, disjoint: a job that fails twice and then completes adds 2 and 1) to both the summary and the detail, counted while the worker holds a live lease (lease-expiry recoveries, offline-worker releases and deregistrations are not counted; counts start at 0 on deploy). `Worker.jobs_processed` / `jobs_failed` are `undefined` against an older backend and the UI then shows nothing (never a made-up 0): the list shows Processed and Failed tiles, the detail's Performance card shows both and the success rate `workerSuccessRate` = processed / (processed + failed), a dash before the worker has finished anything.

## Organization deletion

`DELETE /api/v1/organizations/{id}` (204) is offered as a Danger zone card at the bottom of Organization Settings (`DeleteOrganizationSection`), only when `GET /auth/me` says the key is unrestricted (`isUnrestrictedKey`: empty `queues` or a `*` entry, the backend's `queue_scope_is_unrestricted`). Confirmation is typed: the organization slug. The backend refuses with 409 `CONFLICT` while the organization has active jobs (pending, scheduled, processing), workers that are `healthy`/`degraded`/`draining`, or active schedules, and when its Stripe subscription cannot be canceled first (it is canceled before the delete); 403 `ACCESS_DENIED` for a queue-scoped key; 404 for an id that is not the caller's organization. The 409 message names what and how many, and is shown in a card alert (the confirm dialog closes so it stays readable); 403 and 404 get fixed wording (`describeDeleteOrganizationError`). On success the query cache and the session are cleared and the browser goes to `/`: every key of the organization is dead.

## Queues

`GET /api/v1/queues` returns `QueueConfigSummary` (`max_retries`, `default_timeout`, `rate_limit`, `enabled`) with no settings. `transformQueueSummary` (`src/lib/api/queues.ts:93-103`) leaves concurrency, retry delay and backoff undefined, and the list shows only Max Retries and Job Timeout. The detail payload carries `settings`, but the backend does not enforce concurrency, retry delay, backoff or max retry delay. Those controls are therefore not shown or written: the create request sends only the settings the caller set (`queues.ts:187-196`), and detail Save sends description, max retries and job timeout (`src/components/queues/QueueDetailsPage.tsx:349-359`).

Queue stats: `deadletter` maps from `deadletter_jobs` and stays undefined when the backend omits it (`queues.ts:116`). The detail tile shows an em dash in that case (`QueueDetailsPage.tsx:93`), and the Dead Letter tile sits beside Failed (24h) (`:84`, `:92`). The worker count and the No Workers warning use `stats.active_workers`, which counts `queue_names` (`QueueDetailsPage.tsx:169`, `:241`); `queues.ts:117` maps it.

Create Queue (`src/components/queues/CreateQueueDialog.tsx`) is not an upsert from the UI. It calls `GET /queues/{name}` first. An existing queue refuses the create (`QueueExistsError`, `:27-32`, `:52-63`, `:72-74`) and links to its edit page ("Edit it instead", `:161`). Only a 404 goes on to `PUT`. The name rule matches the backend: letters, digits, `_`, `-` and `.`, and no leading dot or dash (`:25`, `:108`). Max retries 0 is kept (`:118`).
